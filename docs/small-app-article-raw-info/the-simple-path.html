Idea → live app

The Simple Path

A practical route from an idea to a website you can change quickly — without losing your work every time you ask the AI for a tweak.

Why your changes keep disappearing

It isn't that AI coding is bad. It's that one giant HTML file gives the AI the whole thing to rewrite on every request — so each "improvement" quietly throws away the last one. One step forward, two steps back.

The fix is two ideas. Everything below is just these two, in order:

  • 1
    Let the AI coder build a real project — separate files it can edit a small piece at a time, instead of one page it has to redo from scratch.
  • 2
    Add Git — save points, so every working version is kept and any bad change can be undone.

Who does what

This is the part that trips people up. You don't write code or organise files. The AI coder does. You stay in plain English the whole way.

Your job

  • Say what you want, in plain English
  • Look at the result in your browser
  • Say what to change next

The AI coder's job

  • Decide the file/folder structure
  • Write and edit all the code
  • Run it locally so you can preview it
Think→Design→Hand to AI coder→Preview locally→Save points→Iterate→Back up→Publish
1

Think it through

Goal: a clear written brief, before anything is built.

  1. Open an AI chat assistant and describe the app in plain English — what it's for, who uses it, what screens it needs, what each screen shows.
  2. Ask it to interview you a couple of questions at a time, then turn the conversation into a front-end design brief.
  3. Keep going until you can read it back and think: "yes — if this existed, that's what I wanted."
2

Design it

Goal: see what it'll look like, and produce something to hand over.

  1. Drop the brief into a design tool — Google Stitch is a good one (v0 and Lovable are alternatives).
  2. It generates sample pages and a design system: the colours, fonts and components your app will use. Tweak them visually until they feel right.
  3. Export the pages as HTML. The export carries that design system with it — that's the package you'll hand to the AI coder.
3

Hand it to the AI coder

Goal: a working version you can preview at a local web address.

  1. Put the exported files in a new folder on your computer. Don't worry about organising them — just drop them in.
  2. Open that folder in VS Code (or open a terminal inside the folder).
  3. Run an AI coder there — Claude Code or OpenAI Codex, via their VS Code extension or the terminal.
  4. Tell it, in plain English:
Turn these exported design files into a working app I can preview locally. You set up the file structure and write the code. When it's ready, run it and tell me the local address to open.
  1. It'll set everything up and start the app running, then give you a local address like http://localhost:3000. Open that in your browser — that's your app.
Remember: you are not arranging files or writing code. The AI coder owns all of that. Your job is to point it at the folder and say what you want.
4

Add save points

Goal: be able to undo any change that breaks things.

  1. Install Git.
  2. Ask the AI coder to set it up and save the current version: "Set up Git in this project and commit this as the first working version."

The AI coder can run all the Git commands for you. If you'd rather do it yourself, it's only these:

# first time
git init
git add .
git commit -m "Initial working version"
The rhythm from here on: make a change → check it in the browser → save it → move on.
5

Iterate with the AI coder

Goal: shape the app, safely, until you're happy.

  1. Tell it what to change, one thing at a time: "Change the dashboard cards to…"
  2. Refresh localhost in your browser and look.
  3. If it's good, commit it. If it broke something, roll back to the last save and try again.
  4. Repeat until it's what you want.

Pasting this into the AI coder prevents the exact problem you had before — it stops it rewriting everything:

Make this change only: [describe the change]. First tell me which files you'll touch and why. Don't rewrite the whole project or change unrelated sections. After editing, summarise what changed and how I should test it.
6

Back it up

Goal: a safe copy online, ready to publish from.

  1. Create a GitHub account and a new private repository.
  2. Ask the AI coder to push your project to it — or use VS Code's Source Control panel.

The commands, if you want them:

git branch -M main
git remote add origin https://github.com/YOUR-NAME/YOUR-REPO.git
git push -u origin main
7

Publish it

Goal: a live URL you can share.

  1. Go to Vercel and sign in with GitHub (Netlify works just as well).
  2. Import your repository and deploy. For a simple site the defaults usually just work.
  3. Open the live URL it gives you and test it. You can add a custom domain later.
8

Add data later — only if needed

Goal: don't overcomplicate version 1.

  1. A prototype, dashboard mock-up or simple site often needs no database — sample data in a file is fine.
  2. Add one only when you need saved data: accounts, logins, form submissions, uploads.
  3. Supabase covers database, logins and storage when that day comes. Treat it as version 2.

A few more prompts worth keeping

For when things go sideways or you want a tidy history.

Debugging. This was working before the last change. Find the smallest likely cause and suggest a minimal fix. Don't refactor unrelated code.
Commit message. Summarise the change I just made as a short Git commit message in plain English.

Traps to avoid

  • Trying to build the finished product in one go. Aim for a first useful version, then improve it.
  • Letting the AI rewrite everything. Use the guardrail prompt — name what it's allowed to touch.
  • Not looking between changes. Refresh the browser after each one.
  • Forgetting to save before a risky change. Commit a working version first.
  • Adding a database too early. Use sample data until you genuinely need saved data.
